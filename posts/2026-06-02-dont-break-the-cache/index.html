A batch identifier looks like harmless bookkeeping. In our review-labeling test, placing it before the repeated instructions prevented that block from being cached. Moving it after the static content reduced the observed cost by about 26%.

Each request asked DeepSeek to label ten German customer reviews using the same instructions and list of 23 topics. Most of that setup stayed unchanged between requests. The new reviews, and a batch identifier where included, were the changing parts.

The experiment showed why prompt optimization needs to account for more than length. Reordering a field could make repeated text cheaper to process. Compressing a topic list could send fewer tokens yet increase the bill if cache reuse disappeared.

What the cache reuses

The prefix is the beginning of a request. When successive requests start with the same content, prefix caching can reuse processing associated with that shared beginning. A changing field placed early can interrupt the match before the instructions or topic list are reached.

For this labeling task, the request can be understood as two blocks:

UNCHANGED BETWEEN REQUESTS
  System instructions
  Labeling rules
  Fixed topic list, in a fixed order
  Required response format

CHANGING BETWEEN REQUESTS
  Batch identifier, if needed
  Ten new customer reviews

The cache does not supply a saved answer for the new reviews. The model still generates their labels, and output tokens are billed separately. The API reports reused input as prompt_cache_hit_tokens and the remaining input as prompt_cache_miss_tokens.

At the prices saved for this experiment, a million cached input tokens cost $0.0028, compared with $0.14 for uncached input: a 50-fold difference. That explains how a moderately longer request could be cheaper if enough of it was reused. The complete rates and cost calculation are retained in the methods note below; the provider’s pricing page lists current rates.

This is the warm-up pattern we observed, not a promise that caching always starts on the third request. Cache availability is best-effort provider behavior; the DeepSeek caching guide describes the feature.

Two measurements help separate cost from behavior. The overall cached share includes every request, including warm-up, and is the percentage used in the opening table. The steady-state measurements exclude the first three requests so we can inspect reuse after warm-up. In this run, 48.8% of all input was cached; after excluding those requests, the share was 53.3%. These are shares of input tokens, not percentages of requests that received a hit.

Why a shorter prompt can cost more

An earlier experiment exposed the problem while we were trying to shorten the prompt. One version kept complete topic and category names. A second shortened JSON field names (for example, topic_id became t) while retaining the descriptive values. A third removed repeated category names and used short topic codes that Python mapped back to the full hierarchy afterward.

The difference is illustrated by a topic such as staff friendliness. Shortening a field name leaves “Service” and “Staff friendliness” in the prompt. The more aggressive version keeps the topic description but replaces its place in the hierarchy with a code. Both reduce text, but they change different parts of the repeated setup.

This was a separate 1,000-review experiment with reasoning enabled, using batches of ten. Its total costs include reasoning and are therefore much higher than the opening comparison. Compare the variants within this table.

The coded version sent 24.8% fewer input tokens than the original, but none received the discounted cache-hit price. Its input cost rose from $1.44 to $19.82 per million reviews, about 13.8 times higher. Its total cost rose by a much smaller 8.5%, because output and reasoning accounted for most of the bill.

Shorter field names worked better in this comparison: they reduced tokens while retaining cache reuse. That is an observed result for these prompts, rather than a guarantee that one representation will always be cheaper.

The experiment changed several aspects of the request, including its length, representation, and, in additional variants, schema placement. It revealed the tradeoff but did not isolate why a particular version stopped receiving hits. The two diagnostic experiments below were designed to examine that behavior more directly.

What determines how much input gets reused?

The production layouts showed the cost difference. Two smaller diagnostic tests examined the amount of unchanged content and the position of the first changing field. Each configuration used 20 batches of ten reviews with reasoning disabled; the charts report median cached tokens after excluding the first three batches.

How much unchanged content comes first?

The first test began with a minimal one-topic prompt and added increasing amounts of identical filler text before the reviews. This artificial setup made it possible to explore short prefixes; the full production prompt was already long enough to receive hits.

Without padding, the prompt received no hits in 20 requests. The first padded setting, targeting 128 added tokens, received 256 cached tokens on every one of the 17 steady-state requests. The total reusable beginning included the instructions as well as the added padding, which is why those two numbers differ.

This experiment does not establish that adding filler saves money. It measured reuse, and extra padding still has a cost. For an actual labeling job, the useful action is to preserve the instructions and reference material already needed, then measure the bill.

Where does the first changing field appear?

The second test kept a large prompt fixed and inserted a line containing the changing batch number at different positions. If that line appeared within the first 192 words, the API reported no cache hits. Placing it later preserved more reuse: at the tested positions of 256, 1,024, and 2,048 words, the median reported hits were 256, 1,024, and 2,048 tokens respectively. Without the inserted field, the median was 3,328 tokens.

Here the insertion positions are measured in words, while the API reports reuse in tokens. The numerical matches at those settings are specific to the test text; words and tokens are not interchangeable units. The practical result is that moving the changing field later left more of the beginning available for reuse. Identical text after that field did not restore the lost benefit.

Across both scans, the smallest nonzero reported hit was 256 tokens and every nonzero hit count was a multiple of 128. Those observations are consistent with reuse in discrete units, but they do not establish a universal 256-token minimum or uniquely identify a 128-token cache implementation. They describe this model and workload on the experiment date.

A prompt layout to use and verify

For this workload, a useful starting layout is:

Fixed instructions → fixed topic list → fixed response format → changing metadata → new reviews.

The batch-identifier example shows why the boundary matters. A field can be useful for tracking requests without occupying the first line. Likewise, a topic list can retain its meaning while changing its order, but that change may prevent reuse.

When building or revising a labeling prompt:

  1. Keep repeated content consistent. Use the same topic order, section names, and formatting between requests.
  2. Place changing fields after the reusable block. Check batch identifiers, timestamps, and other per-request metadata as well as the review text.
  3. Measure after a change. Inspect cache-hit and cache-miss tokens, output tokens, and total cost; a shorter prompt or a higher cached percentage alone does not establish a saving.
  4. Check representative requests after warm-up. Inspect several batches to understand reuse, while including the initial requests in the total bill.

These tests measured cache behavior and cost, not labeling quality or latency. A prompt change still needs to produce useful labels. The result worth carrying into another workload is the testable layout principle: keep the necessary repeated content together at the beginning, then verify what the provider actually reuses.

Methods, historical pricing, and sources

Scope. The controlled experiments used deepseek-v4-flash on May 31, 2026, with reasoning disabled and 200 reviews per configuration. Production validation used the fixed 23-topic taxonomy; the padding test used a minimal one-topic prompt. The earlier format comparison used 1,000 reviews per variant with reasoning enabled. All used ten reviews per batch. A run-specific identifier in the system message was held constant within each controlled run and changed between runs to separate their cache prefixes.

Historical rates. The saved cost rollup used the following prices, recorded on May 31, 2026. These are experiment inputs, not current pricing. Model versions, rates, and caching behavior can change.

Token class USD per million tokens
Cached input $0.0028
Uncached input $0.14
Output $0.28

Calculation. Costs use provider-returned input cache-hit, input cache-miss, and completion-token counts. Scaling to a million reviews divides the run cost by its review count and multiplies by one million.

run_cost = (
    cached_input_tokens × 0.0028
  + uncached_input_tokens × 0.14
  + output_tokens × 0.28
) / 1,000,000

uncached_comparison = (
    all_input_tokens × 0.14
  + output_tokens × 0.28
) / 1,000,000

The uncached comparison holds the run’s input and output counts fixed. It changes only the price applied to cached input. The measured output includes reasoning tokens where reasoning was enabled.
